# ADR-0032 — Notification Routing and Event Separation

> **Status:** Accepted  
> **Date:** 2026-07-03  
> **Sprint:** SPR-006 — EN-001  
> **Decided by:** Project owner (Sprint 006 authorisation)  
> **Related:** [Document 021](../021-notification-activity-attention-management-framework.md) · [ADR-0031](./ADR-0031-event-registry-and-bus.md) · [Notification Framework](../architecture/notification-framework.md)

## Problem

Document 021 states: **modules never send notifications** — modules publish events; platform services determine whether notifications are created.

Sprint 006 must formalise:

1. Notification taxonomy separate from Event taxonomy
2. Delivery channels separate from event categories
3. Mapping layer between Event Bus and Notification Registry
4. Which notification categories/channels are in SPR-006 scope

Conflating events with notifications (e.g. treating a toast as an event type) would invert the dependency graph and violate Platform 3.0 design patterns.

## Decision

### Architectural principle (locked)

```text
Platform Capability
        ↓
Domain Event
        ↓
Platform Event Bus
        ↓
Notification Mapping
        ↓
Notification Experience
```

| Rule                                               | Enforcement                                      |
| -------------------------------------------------- | ------------------------------------------------ |
| Events and Notifications are **separate concepts** | Separate registries, types, APIs                 |
| Notifications **consume** events                   | `EventToNotificationMapper` subscribes to bus    |
| Events are **never** generated by Notifications    | Code review + no publish in notification modules |
| Modules **never** send notifications directly      | No public `sendNotification()` on capability SDK |

### Notification taxonomy (canonical categories)

Notifications are classified by **presentation intent** — not by event type:

| Category | `notificationKind` | Description                             | SPR-006       |
| -------- | ------------------ | --------------------------------------- | ------------- |
| Toast    | `toast`            | Transient, auto-dismiss surface message | Scaffold      |
| Banner   | `banner`           | Persistent top-of-shell alert           | Scaffold      |
| Inbox    | `inbox`            | Durable item in notification inbox/list | ✅ Foundation |
| In-App   | `in-app`           | General in-application delivery (panel) | ✅ Foundation |

Future categories (documented, not implemented in SPR-006):

| Category | `notificationKind` | Channel layer       |
| -------- | ------------------ | ------------------- |
| Email    | `email`            | External delivery   |
| SMS      | `sms`              | External delivery   |
| Push     | `push`             | Mobile/desktop push |
| Webhook  | `webhook`          | HTTP callback       |

**Notification category ≠ Event category.** A single `capability` event may map to `inbox` + `toast` via separate routes.

### Delivery channels (separate from events)

Delivery channels describe **how** a notification reaches the user — orthogonal to event taxonomy:

| Channel id | Description                   | SPR-006           |
| ---------- | ----------------------------- | ----------------- |
| `in-app`   | Desktop Shell notification UI | ✅ Implemented    |
| `email`    | SMTP / provider delivery      | ⏳ Interface stub |
| `sms`      | SMS provider                  | ⏳ Interface stub |
| `push`     | Mobile/desktop push           | ⏳ Interface stub |
| `webhook`  | Outbound HTTP                 | ⏳ Interface stub |

Each **NotificationRoute** declares:

```yaml
notifications:
  routes:
    - id: platform.action.executed.inbox
      eventPattern: capability.action.executed
      notificationKind: inbox
      channel: in-app
      priority: normal
      templateRef: action-executed
      permission: platform.notifications.read
```

### Notification Registry

**NotificationRegistry** stores route **metadata** — not live notification instances.

Live notifications live in **NotificationSessionStore** (in-memory SPR-006), populated by mappers reacting to events.

### Mapping layer

**EventToNotificationMapper**:

1. Subscribes to registered event patterns on InProcessEventBus
2. Looks up matching NotificationRoutes
3. Applies template + priority rules
4. Creates `NotificationItem` DTO in session store
5. Does **not** publish new events (no feedback loop)

### Public API boundary

**NotificationService** is the sole client-facing API for Experiences:

- `useNotificationService()` — mandatory public hook (mirrors `useKnowledgeService()`)
- Experiences **must not** subscribe to Event Bus directly

### SPR-006 scope

| In scope                | Out of scope                         |
| ----------------------- | ------------------------------------ |
| `in-app` channel        | Email, SMS, push, webhook delivery   |
| `inbox`, `in-app` kinds | Full toast/banner UX polish          |
| Mapper scaffold         | Attention Engine full implementation |
| Badge count             | Digest, quiet hours                  |

## Alternatives

| Alternative                                | Why rejected                                      |
| ------------------------------------------ | ------------------------------------------------- |
| Toast as event type                        | Conflates concepts; breaks consumer/producer rule |
| Module calls NotificationService           | Violates Document 021                             |
| Event Bus subscribes to notifications      | Inverted dependency                               |
| Single registry for events + notifications | Loses separation of concerns                      |

## Consequences

- EN-007–EN-009 implement Notification Registry, routes, mappers
- EN-011 implements NotificationService; EN-012–EN-013 implement Experiences
- Email/SMS/push/webhook channels registered as `planned` routes — Delivery Service deferred
- Activity Framework (M7) subscribes to same events independently — parallel consumer, not via notifications
- Knowledge Framework may consume events for ranking — optional subscriber, not notification path

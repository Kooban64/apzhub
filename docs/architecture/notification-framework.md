## Purpose

The **Notification Framework** is the platform layer responsible for **determining who receives what information, when, and through which channel** — based on platform events, routes, and attention rules.

Notifications are a **delivery mechanism**. Attention management is the platform capability (Document 021).

**Modules never send notifications.** Modules publish events. The Notification Framework maps events to notifications.

**EN-001 scope:** Architecture and taxonomy. **Implementation:** EN-007–EN-016 (Notification Registry, Mapper, Service, Presentation Layer, Experiences, app integration, E2E verification).

---

## Architectural principle

```text
Platform Capability
        ↓
Domain Event
        ↓
Event Bus
        ↓
Notification Mapping
        ↓
Notification Service
        ↓
Notification Presentation Layer
        ↓
Notification Experiences
```

| Rule                                    | Meaning                                   |
| --------------------------------------- | ----------------------------------------- |
| Notifications consume events            | Via EventToNotificationMapper             |
| Events never generated by notifications | No publish in notification modules        |
| Delivery channels ≠ event categories    | Orthogonal taxonomies                     |
| Public API is NotificationService       | Experiences do not subscribe to Event Bus |

        ↓

        ↓

| --------------------- | ------------------------ | ----------------- |

## Notification taxonomy

Notifications are classified by **presentation intent** (`notificationKind`). This taxonomy is **independent** of Event categories.

### Toast (`toast`)

Transient, auto-dismiss message — low interruption.

| Example                  | Trigger event                | Channel                 |
| ------------------------ | ---------------------------- | ----------------------- |
| "Theme switched to dark" | `capability.theme.changed`   | `in-app` (toast region) |
| "Action completed"       | `capability.action.executed` | `in-app` (toast region) |

**SPR-006:** Scaffold — interface registered; minimal UI.

### Banner (`banner`)

Persistent top-of-shell alert — requires explicit dismiss.

| Example                              | Trigger event                       | Channel                |
| ------------------------------------ | ----------------------------------- | ---------------------- |
| "Platform maintenance in 15 minutes" | `system.platform.health.degraded`   | `in-app` (banner slot) |
| "Connector sync failed"              | `integration.connector.sync.failed` | `in-app` (banner slot) |

**SPR-006:** Scaffold — route metadata only.

### Inbox (`inbox`)

Durable notification list item — survives until read or archived.

| Example                                        | Trigger event                          | Channel          |
| ---------------------------------------------- | -------------------------------------- | ---------------- |
| "Action audit: platform.theme.toggle executed" | `capability.action.executed`           | `in-app` (inbox) |
| "New assignment from Plane"                    | `capability.plane.task.assigned` (M9+) | `in-app` (inbox) |

**SPR-006:** ✅ Foundation — primary notification kind for shell panel.

### In-App (`in-app`)

General in-application delivery — notification panel, popover, badge source.

| Example                 | Trigger event                   | Channel  |
| ----------------------- | ------------------------------- | -------- |
| Unread count badge      | aggregate of inbox items        | `in-app` |
| Notification panel list | all active in-app notifications | `in-app` |

**SPR-006:** ✅ Foundation — NotificationPanelExperience + BadgeExperience.

### Email (`email`)

External delivery via email provider — **not** an event type.

| Example              | Route                                  | Channel |
| -------------------- | -------------------------------------- | ------- |
| Daily digest summary | scheduled mapper (future)              | `email` |
| Security alert       | `security.session.suspicious` (future) | `email` |

**SPR-006:** ⏳ Interface stub — Delivery Service deferred M8+.

### SMS (`sms`)

External delivery via SMS provider.

| Example               | Route                              | Channel |
| --------------------- | ---------------------------------- | ------- |
| MFA verification code | `security.mfa.code.requested` (M8) | `sms`   |

**SPR-006:** ⏳ Interface stub.

### Push (`push`)

Mobile or desktop push notification.

| Example                  | Route                                | Channel |
| ------------------------ | ------------------------------------ | ------- |
| Urgent approval required | `capability.approval.required` (M9+) | `push`  |

**SPR-006:** ⏳ Interface stub.

### Webhook (`webhook`)

Outbound HTTP callback to external systems.

| Example              | Route                              | Channel   |
| -------------------- | ---------------------------------- | --------- |
| Notify external ITSM | `integration.ticket.created` (M9+) | `webhook` |

**SPR-006:** ⏳ Interface stub.

Full taxonomy: [SPR-006-ENF-notification-architecture.md](../specs/SPR-006-ENF-notification-architecture.md) §4.

## Delivery channels (separate from events)

Delivery channels describe **transport** — how a notification reaches the user. One event may fan out to multiple channels via separate routes.

| Channel id | Transport                     | SPR-006 |
| ---------- | ----------------------------- | ------- |
| `in-app`   | Desktop Shell notification UI | ✅      |
| `email`    | SMTP / email provider         | ⏳ Stub |
| `sms`      | SMS gateway                   | ⏳ Stub |
| `push`     | FCM/APNs/desktop push         | ⏳ Stub |
| `webhook`  | HTTP POST to registered URL   | ⏳ Stub |

```text
Event: capability.action.executed
        │
        ├──► Route A: kind=inbox,  channel=in-app  ──► Shell panel
        └──► Route B: kind=email,  channel=email   ──► (deferred) Delivery Service
```

**Event category (`capability`) does not imply channel (`email`).** Mapping is explicit in NotificationRoute.

## NotificationService (public API — implemented)

| Method                        | Purpose                        |
| ----------------------------- | ------------------------------ |
| `listNotifications(options?)` | Active notifications for actor |
| `markRead(notificationId)`    | Mark read                      |
| `markAllRead()`               | Clear unread                   |
| `subscribe(onChange)`         | In-process listener            |
| `getDiagnostics()`            | Dev snapshot                   |

Hook: `useNotificationService()` and `useNotificationPresentation()` — mandatory public APIs for Experiences.

Experiences **must not** import Event Bus or mapper internals.

## Registry Pattern compliance

1. **Declaration** — manifest `notifications.routes` block
2. **Server bootstrap** — `bootstrapNotificationRegistry()`
3. **Permission filter** — `filterNotificationRegistryDto()`
4. **Hydration** — notification items + route metadata to client
5. **Execution** — action delegation via existing `execute()` only

## Relationship to Event Framework

The Notification Framework **depends on** the Event Framework — not vice versa.

```text
InProcessEventBus
        ↓ subscribe
Notification Mapping
        ↓ write
Notification Service
        ↓ read
Notification Presentation Layer → Notification Experiences
```

See [event-framework.md](./event-framework.md).

---

## Relationship to Activity Framework (M7)

Activity and Notification are **parallel consumers** of events:

```text
                    Event Bus
                   /         \
                  /           \
    NotificationMapper    ActivitySubscriber (M7)
```

Activity timeline is **not** implemented in SPR-006. Interface stub only.

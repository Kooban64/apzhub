# Acceptance Criteria Standard

> **Programme:** APZHUB-PRODUCTS-004

## Purpose

Every requirement shall have testable acceptance criteria and participate in Ready/Done and approval discipline.

## Per-requirement acceptance criteria

Acceptance criteria must be:

- **Specific** — observable outcome
- **Testable** — can fail in a test or review
- **Unambiguous** — no “should work well” without measure
- **Scoped** — matches the requirement ID

Preferred formats: Given/When/Then or bullet checklist.

## Definition of Ready (requirement item)

A requirement is Ready when:

- [ ] ID, statement, priority, risk present
- [ ] Acceptance criteria present
- [ ] Stakeholder owner identified (if SR/FR)
- [ ] Dependencies / Platform freezes noted
- [ ] Open questions resolved or explicitly deferred

## Definition of Done (later delivery — recorded at Requirements for intent)

Delivery of a requirement is Done when (intent for later stages):

- [ ] Implemented within approved programme scope
- [ ] Tests prove acceptance criteria
- [ ] Docs/limitations updated
- [ ] Traceability matrix updated
- [ ] No brand-mask or layering defects

## Approval workflow

See Requirements Engineering Standard approval states. Baseline Approval is required before Product Definition.

## Priority and risk

Every requirement must carry Priority (P0–P3) and Risk (Critical–Low). Aggregates appear in the baseline summary.

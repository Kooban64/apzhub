## Overview

This release delivers the APZHUB **Workbench Framework** (`@apzhub/workbench-framework`): the registry-aware, session-capable user interaction layer that hosts all future platform and business capabilities.

Capabilities publish **Workbench Requests** through the **Workbench API**; the Workbench Manager orchestrates layout, navigation, views, sessions, context, and selection — without exposing engine internals.

---

## Highlights

### Workbench Framework package

New package `@apzhub/workbench-framework` with:

- **Workbench Manager** — request routing, state coordination, permission gate
- **Request Bus** — typed Workbench Request transport (ADR-0020)
- **Layout Engine** — shell region geometry and dock splits
- **Panel Engine** — region visibility, collapse, resize
- **Navigation Engine** — registry-driven Activity Bar and sidebar (ADR-0022)
- **View Engine** — view activation and route mapping
- **Session Engine** — versioned client session persistence (ADR-0021)
- **Context Engine** — context panel state orchestration
- **Selection Engine** — per-view selection state

### Workbench API v1.0

```typescript
import {
  createWorkbenchAPI,
  useWorkbenchAPI,
  type WorkbenchAPI,
  type WorkbenchAction,
} from "@apzhub/workbench-framework";

// Capabilities and shell use WorkbenchAPI — not engines directly
await api.navigate({ workspaceId: "..." });
await api.openView({ viewId: "..." });
await api.executeAction(action);
```

### Permission integration

- `createWorkbenchPermissionAdapter()` — scaffold (dev) and auth adapters
- `filterWorkbenchRegistryDto()` — server-side registry filtering before client hydration
- Session restore re-validates persisted state against permission adapter

### Application integration

- Registry hydration from Platform Runtime at server bootstrap
- React providers: `WorkbenchShellProvider`, `useWorkbenchAPI()`
- Activity Bar and sidebar driven by manifest `workbench.navigation`
- Client route sync with session restore

### Engineering Constitution

- Document 000 §6.1 — permanent **API layering model**: Runtime API → Workbench API → Capability API

## Architectural improvements

- Clear separation: Platform Runtime (UI-agnostic) vs Workbench Framework (React orchestration)
- Capability integration exclusively via Workbench Requests — no direct shell manipulation
- Server-side permission filtering prevents disallowed registry entries reaching the client
- Versioned session schema with restore sanitisation
- Workbench Actions and Command Bridge interface prepared for Sprint 004

---

## Breaking changes

**None** for SPR-001 or SPR-002 consumers.

- Workbench APIs are additive
- Desktop Shell layout preserved — enhanced incrementally, not rewritten
- Existing scaffold manifests remain valid; `workbench.navigation` / `workbench.view` blocks are optional extensions

---

## Known limitations

1. **Tab bar** — session tracks focused view only; multi-tab UI not rendered
2. **View content** — placeholder region; capability view mount pipeline not implemented
3. **RBAC** — `AuthWorkbenchPermissionAdapter` structure ready; permission keys populated in Milestone 8
4. **Session sync** — localStorage only; PostgreSQL/server sync deferred
5. **Command Framework** — keyboard shortcuts, command palette, AI command execution — Sprint 004
6. **Context panel / selection** — engines implemented; full shell UI wiring pending
7. **Deep links** — client route sync only; SSR hydration guard not implemented

---

## Upgrade notes

1. Add `@apzhub/workbench-framework` where workbench integration is required
2. Ensure `Runtime.bootstrap()` completes before workbench hydration
3. Use `filterWorkbenchRegistryDto()` on the server when passing registry data to the client
4. Inject permission adapter via `createWorkbenchPermissionAdapter({ mode: "auth" | "scaffold" })`
5. Capabilities must use `WorkbenchAPI` — do not import engine classes for orchestration

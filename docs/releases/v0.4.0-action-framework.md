## Overview

This release delivers the APZHUB **Action Framework** (`@apzhub/command-framework`): unified action registration, discovery, permission filtering, and execution across Command Palette, keyboard shortcuts, context menus, toolbar, and Workbench API.

All user-facing command surfaces in the Desktop Shell now consume a **single hydrated Action Registry** and execute through **one shared `DefaultActionExecutor`**.

---

## Major features

### `@apzhub/command-framework` package

- **ActionRegistry** — manifest and catalogue registration, search, context filtering
- **DefaultActionExecutor** — permission gate, actor model, audit hook, gateway routing
- **WorkbenchCommandBridge** — translates bridge action ids to `WorkbenchAction`
- **ShortcutRegistry** — chord normalisation, conflict detection
- **Server bootstrap** — `bootstrapActionRegistry`, `filterActionRegistryDto`
- **Client hydration** — `createCommandRegistryFromDto`, read-only client registry
- **Platform Action Catalogue** — built-in workbench actions (`workbench.view.open`, etc.)
- **Platform Asset extraction** — toolbar regions and shortcuts from manifests

## Architectural improvements

- **Single execution pipeline** — palette, shortcuts, toolbar, context menu, and Workbench API share one executor
- **Server-authoritative registry** — permission-filtered DTO before client hydration; no client-side registration mutations
- **Platform vs Capability asset distinction** — built-in catalogue, manifest actions, toolbar regions documented and tested
- **Workbench Surface Pattern** — presentation in `@apzhub/workspace`, execution in `@apzhub/command-framework`
- **Invocation source abstraction** — gateway stubs for AI, voice, and automation (extension points only)
- **Layering preserved** — Action Framework invokes Workbench through bridge; no direct engine access from shell

## User-facing capabilities

Authenticated users on `/workspace/*` can:

- Open the **Command Palette** (Ctrl+Shift+P) and search platform and manifest actions
- Use **keyboard shortcuts** registered from manifests (e.g. Ctrl+Shift+T, Ctrl+Shift+H)
- Access **context menu** actions filtered by selection and surface
- Use the **workspace toolbar** with platform actions (e.g. Toggle Theme)
- Continue using header theme toggle (legacy control — separate from Action Framework toolbar)

---

## Developer-facing capabilities

- Declare actions in manifest `workbench.actions` with palette, shortcut, toolbar, and permission fields
- Bootstrap actions server-side via `bootstrapActionRegistry()`
- Hydrate client registry with `CommandRegistryProvider` + `useCommandRegistry()`
- Wire executor with `createDefaultActionExecutor` + `createDefaultWorkbenchCommandBridge`
- Integrate app shell with `ActionWorkbenchShellProvider` pattern (see AF-020)
- Inspect hydration via `/api/health` `commands` and dev `ActionFrameworkDiagnostics`

See [Action Framework onboarding](../developer/action-framework-onboarding.md).

## Known limitations

1. **Service handlers** — `handler: service:…` actions return `NOT_IMPLEMENTED` (e.g. `platform.theme.toggle` does not invoke theme service yet)
2. **Manifest bridge ids** — manifest actions using `workbench-bridge:` handlers may not resolve if action id differs from bridge id (TD-AF20-01)
3. **RBAC** — permission keys declared; full session permission population deferred to Milestone 8
4. **AI / voice / automation** — gateway stubs only; actors route to `NOT_IMPLEMENTED`
5. **Client sync** — one-way server → client hydration; delta synchronisation not implemented
6. **Header vs toolbar theme** — duplicate theme controls (header button + toolbar action)
7. **Production diagnostics UI** — hidden in production; use health endpoint for ops
8. **User shortcut overrides** — Document 023 preferences not wired

## Breaking changes

**None** for SPR-001, SPR-002, or SPR-003 consumers.

- Action Framework APIs are additive
- Workbench API v1.0 preserved; `resolveActionExecutor` is optional on `WorkbenchProvider`
- Existing manifests without `workbench.actions` remain valid

## Upgrade notes

1. Add `@apzhub/command-framework` where action integration is required
2. Ensure `Runtime.bootstrap()` completes before `bootstrapActionRegistry()`
3. Server: `filterActionRegistryDto(dto, permissionAdapter)` before passing to client
4. Client: wrap shell in `CommandRegistryProvider` with shared `ActionExecutor`
5. Enable Desktop Shell surface flags as needed (`enableCommandPalette`, etc.)
6. Add `@apzhub/command-framework` and `@apzhub/workbench-framework` to Next.js `transpilePackages`

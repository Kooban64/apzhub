## Executive summary

This release delivers the APZHUB **Knowledge & Discovery Framework** (`@apzhub/knowledge-discovery-framework`): unified Knowledge Source registration, multi-provider query orchestration, ranking, client hydration, and the public **Knowledge Service** API for Knowledge Experiences.

Authenticated shell integration wires the Knowledge Service behind `KnowledgeDiscoveryProvider`. Command Palette knowledge mode and Knowledge Overlay consume ranked documents through the Knowledge Presentation Layer. Selection delegates through existing Action Framework and Workbench navigation — no new execution pipeline.

---

## New platform capabilities

### `@apzhub/knowledge-discovery-framework` package

- **Knowledge Registry** — bootstrap, validation, metadata, server DTO map/filter
- **Knowledge Providers** — Action Registry and Workbench navigation projections
- **KnowledgeDiscoveryOrchestrator** — multi-provider query, merge, dedupe, diagnostics
- **RankingEngine** — keyword and fuzzy strategies; planned strategy scaffolds
- **Knowledge Service** — public client boundary (`createKnowledgeService()`, `useKnowledgeService()`)
- **Client hydration** — `KnowledgeDiscoveryProvider`, `useKnowledgeRegistry()`
- **Server bootstrap** — `bootstrapKnowledgeRegistry()`, permission-filtered DTO

### Knowledge Experiences (`@apzhub/workspace`)

| Experience                     | Status                                      |
| ------------------------------ | ------------------------------------------- |
| Knowledge Overlay              | ✅ Implemented — modal Knowledge Experience |
| Command Palette knowledge mode | ✅ Implemented — `mode="knowledge"`         |

## Architecture overview

```text
Knowledge Sources
        ↓
Knowledge Registry
        ↓
Knowledge Query API (internal)
        ↓
Knowledge Service ← useKnowledgeService() [public]
        ↓
Knowledge Presentation Layer
        ↓
Knowledge Experiences
        ↓
Action execute() · Workbench navigation
```

## Developer features

- Declare Knowledge Sources in manifest `knowledge.sources`
- Implement Knowledge Providers projecting registry DTOs into `KnowledgeDocument` references
- Consume **`useKnowledgeService()`** in Knowledge Experiences — not the orchestrator
- Reuse Presentation Layer: `groupKnowledgeDocuments()`, `delegateKnowledgeOverlaySelection()`
- Wire app shell with `createKnowledgeServiceFromHydration()` pattern (see DF-015)
- Inspect hydration via `/api/health` `knowledge` and dev `KnowledgeDiscoveryDiagnostics`
- E2E verification: `testing/playwright/e2e/spr-005-knowledge-discovery-framework.spec.ts`

See [Knowledge & Discovery onboarding](../developer/knowledge-discovery-onboarding.md).

## User-facing capabilities

Authenticated users on `/workspace/*` benefit from platform knowledge infrastructure:

- **Health observability** — operators can verify knowledge hydration via `/api/health`
- **Command Palette knowledge mode** — available when enabled (test hook: `?paletteMode=knowledge`; product default remains commands mode)
- **Knowledge query path** — platform actions and navigation discoverable through Knowledge Service when knowledge mode is active

Global header search and Knowledge Overlay modal are **not** activated in the default Desktop Shell — provider and Presentation Layer are ready for product activation.

## Upgrade considerations

### For platform engineers

1. Add `@apzhub/knowledge-discovery-framework` to `transpilePackages` if integrating in Next.js apps (already done in `apps/web`)
2. Hydrate knowledge DTO server-side with `filterKnowledgeSourceRegistryDto()` before client delivery
3. Mount `KnowledgeDiscoveryProvider` with `service` prop (preferred) or internal query client for tests
4. Ensure `CommandRegistryProvider` and `WorkbenchProvider` ancestors for Experience selection handlers

### For capability authors

1. Optional: declare `knowledge.sources` in manifests for future provider wiring
2. Continue using `workbench.actions` and `workbench.navigation` — providers project these automatically at platform tier
3. Do not implement custom search execution pipelines — route selections through Action Framework

### Quality gates

All consuming packages should maintain:

```bash
pnpm lint && pnpm typecheck && pnpm build
pnpm test && pnpm test:coverage && pnpm test:e2e
```

## Known limitations

1. In-process orchestrator only — no HTTP query adapter
2. Knowledge Overlay not mounted in default Desktop Shell
3. Keyword + fuzzy ranking only — semantic/AI scaffolds not active
4. Global header search deferred
5. `useKnowledgeQuery()` deprecated but present
6. E2E palette knowledge mode uses `?paletteMode=knowledge` test hook

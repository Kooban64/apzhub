## Executive summary

This release delivers the APZHUB **Event & Notification Framework** (`@apzhub/event-notification-framework`): unified Event Registry and in-process Event Bus, Notification Registry and Mapper, Notification Service, Notification Presentation Layer, and in-app Notification Experiences integrated with the Action Framework audit hook.

Authenticated shell integration wires notification providers behind `ActionWorkbenchShellProvider`. Notification Badge and Panel consume presentation view models through `useNotificationPresentation()`. Successful action execution publishes `capability.action.executed` and surfaces in-app notifications — no new execution pipeline.

---

## New platform capabilities

### `@apzhub/event-notification-framework` package

- **Event Registry** — bootstrap, validation, platform catalogue, server DTO map/filter
- **In-Process Event Bus** — envelope validation, synchronous subscriber dispatch
- **Notification Registry** — route metadata, template refs, permission-filtered DTO
- **DefaultNotificationMapper** — event pattern matching, template rendering
- **DefaultNotificationService** — session store, list, mark read, subscribe, diagnostics
- **Notification Presentation Layer** — view models, priority grouping, relative timestamps
- **React providers** — `NotificationRegistryProvider`, `NotificationServiceProvider`, hooks
- **Action audit integration** — `createActionAuditEventBusHook`, production subscriber wiring

### Notification Experiences (`@apzhub/workspace`)

| Experience                                  | Status                                     |

| Notification Badge                          | ✅ Unread count; opens panel               |
| Notification Panel                          | ✅ Grouped list; mark read / mark all read |

## Developer features

- Declare platform events in catalogue or manifest `events` blocks
- Register notification routes with `eventPattern`, `notificationKind`, `channel`, templates
- Use Action audit hook for automatic `capability.action.executed` events
- Consume **`useNotificationPresentation()`** in Notification Experiences — not Event Bus internals
- Wire app shell with `createAppEventNotificationContext()` + `wireAppEventNotifications()` pattern
- Inspect hydration via `/api/health` `events` / `notifications` and dev diagnostics
- E2E verification: `testing/playwright/e2e/spr-006-event-notification-framework.spec.ts`

See [Event & Notification onboarding](../developer/event-notification-onboarding.md).

## User-facing capabilities

Authenticated users on `/workspace/*` benefit from platform notification infrastructure:

- **Notification badge** — unread count when notifications exist
- **Notification panel** — inbox items from successful action execution; priority grouping; relative timestamps
- **Mark read** — per-item and mark-all-read with badge sync
- **Health observability** — operators verify event/notification hydration via `/api/health`

Dedicated toast popover and banner regions are **not** activated — toast route items appear in the panel list. External delivery (email, SMS, push) is **not** implemented.

## Upgrade considerations

### For platform engineers

1. Add `@apzhub/event-notification-framework` to `transpilePackages` if integrating in Next.js apps (already done in `apps/web`)
2. Hydrate event/notification DTOs server-side with filter functions before client delivery
3. Mount `NotificationRegistryProvider` + `NotificationServiceProvider` with shared service instance
4. Attach `createActionAuditEventBusHook` to Action Executor for audit → notification flow
5. Enable shell Experiences via `enableNotificationBadge` / `enableNotificationPanel` on DesktopShell

### For capability authors

1. Declare `events` in manifest when publishing domain events
2. Declare `notifications.routes` for event → notification mapping
3. Do **not** call Notification Service directly — publish events instead
4. Use `channel: in-app` for shell delivery in M6 scope

### Operational

- Poll `/api/health` for `events.subscriberCount` and `notifications.mapperStatus`
- Diagnostics hooks are dev/test only — absent in production UI
- E2E CI requires `NEXT_PUBLIC_E2E_TEST_HOOKS=true` in Playwright webServer env
